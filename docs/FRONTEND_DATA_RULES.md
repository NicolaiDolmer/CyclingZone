# Frontend server data

SSOT for the incremental #6494 migration onto one data layer (TanStack Query). Pages move one at a time.

## Ownership and scope
- Migrated pages read through typed hooks in `frontend/src/data/`; the page owns filters, dialogs and pending feedback, never a direct `supabase.from(` or `fetch` call.
- One lazily created browser runtime (`useDataScope.ts` `appRuntime()`) owns the QueryClient and stays mounted for focus/reconnect events. A migrated page renders inside `DataProvider` (`DataProvider.tsx`), or its hooks pass `runtime.client` to `useQuery` explicitly (market, auctions, Dashboard). While migration is page by page the provider wraps the page, not the app, so unmigrated routes and the public landing/prerender graph never load Query. Server renders get a separate runtime and never share private data.
- Private keys come from `queryRuntime.ts`: `privateKey(scope, resource, ...)` holds auth generation, viewer, team, resource and parameters; `viewerKey` keeps the team slot empty for data that does not depend on the team, so the key stays stable while the team bootstrap resolves. Tokens and e-mail addresses never enter keys. A real viewer or team change cancels and clears every private key; a same-viewer token refresh keeps the generation.
- Unknown auth blocks private reads. The viewer-scoped team bootstrap precedes team-scoped reads. Cached team data remains available after a background failure; initial bootstrap failure terminates loading and exposes retry.
- Reads call `runtime.beforeRead` and `runtime.assertReadCurrent`, so an answer that arrives after a viewer/team change or a write is discarded. A read whose transport cannot abort does not consume Query's signal, so a remount joins the in-flight read instead of starting a second one.
- Writes bind to the captured viewer (`beginWrite`), never retry automatically, cancel older reads and hold new reads until they settle. Money and successful bids stay server-confirmed.
- Freshness is 30 seconds, inactive retention five minutes, no automatic retry. No polling, persistence, broadcast cache, service-worker data cache or offline write queue.
- Failures never become successful empty lists (`apiQuery.ts`). API transport preserves existing 401 handling, Retry-After, cancellation and network errors. Known data stays visible on a failed background refresh; the page's existing error state shows only when there is nothing to show. An initial settled Retry-After/unauthorized waiting state keeps a quiet placeholder and the existing manual retry action; no automatic retry timer is added.

## Migrated pages
- Global Rank (`/standings?tab=global`, `globalRankData.ts` + `useGlobalRankData.ts`): read-only, no realtime. The rankings hub loads the tab lazily so the league tab does not load Query.
- Transfer market (`/transfers`, `marketData.ts`): listings, sent/received/archived offers and swaps, shape validation and ability normalization.
- Auctions (`/auctions`, `auctionData.ts` + `auctionRealtime.ts`): see below.
- Dashboard (`/dashboard`, `dashboardData.ts`, `todayStagesData.ts`, `dashboardCards.ts`, policy in `dashboardQueryPolicy.ts`): see below.

## Dashboard resources
- One key per page-owned resource (`dashboard:core`, `dashboard:season`, `dashboard:auctions`, entries, next stage, squad nudge, training status, season-start counts, season recap, the four optional modules, the three push modules, annual meeting, today's strip and the self-fetching cards: global rank widget, career firsts, development transition, survey invite, first-race card). The transfers card reads the market's `transfer-offers` key, so Dashboard and Transfers share one entry.
- Module semantics are unchanged (DASHBOARD_RULES.md §3): only the team bootstrap and the core block (incl. an unreachable board status) raise the page error, and only while nothing is known. Every other module settles to its own absent/empty state; known data survives a failed refresh.
- The live channel (`seasons`, `races`) refreshes exactly the resources the legacy `loadAll` read (`LIVE_RESOURCES`), never the market listings, push modules or cards. Today's strip keeps its existing minute refresh while mounted.
- Writes (season signup, onboarding dismiss, transition dismiss) use the write barrier. The signup confirmation is written to the cache only from the server's answer. Reads the barrier cancelled before they had data are refetched afterwards.

## Market resources
- `auctionData.ts` owns one canonical snapshot for auction rows, current bids/proxies, watchlist and squad availability. `auctionRealtime.ts` synchronously applies whitelisted committed server fields before UI callbacks. Unchanged joins/private fields survive; changed relationship IDs clear stale joins and reconcile the exact auction key. A known bidder with a pending name shows the existing skeleton, never a false no-bids label. Unknown names have one scope-bound lookup per id.
- Pure price/end updates, foreign terminal rows and unrelated foreign bids cause no new reads. Unknown membership/insufficient payloads reconcile only the auction key in leading bounded 400ms windows. Own bid INSERTs additionally reconcile that key to confirm private proxy/budget state; a public bid amount is never treated as a proxy ceiling. Own terminal settlement also reconciles the exact bootstrap-team key. Cash remains explicitly pending until the necessary fresh server reads succeed; cancellation/reverted data cannot confirm it. Failed reconciliation stays pending across remount and can be retried. Monetary requests await reconciliation before entering the write barrier; no price is deducted optimistically.
- Public delta/name/uncertainty publications preserve the combined snapshot's existing dataUpdatedAt, so they do not make private context artificially fresh or suppress focus recovery. Scope generation/viewer/team and disposal epochs fence async results.
- After first migrated route use, existing profile listing readers delegate through `sharedRequestCache` into the same Query listing key. Exact credential snapshots are checked before reuse. Unrelated legacy GET caches keep their owners.
- Watchlist optimism updates the canonical cache and rolls back only the affected rider; reads are cancelled before it changes and reconciled after the write.

## Incremental boundary
Pages not listed above are legacy and keep their own loading, including `sharedRequestCache` and `useRealtimeRefetch` (the Dashboard still uses it as its event transport). Cross-cutting owners rendered on the Dashboard stay legacy until separately migrated: `useActionSummary` (Layout nav badges), `useRacePause`, `useNpsPrompt`, `LockedSalesLine` (Layout/Finance), `useForumHighlights` (Forum), `useHeroAgonyMoment` (race page) and `MyLatestResultCard`'s seen-write. Profile, active-season, scouting and player flags keep their named legacy owners too; do not wrap their existing memo caches in a second Query cache. Concurrent reads of the public player flags endpoint share one transport request only for the same authorization header. Anonymous reads and other tokens stay separate, and a later read fetches again after completion. New data modules and tests are TypeScript. Bundle ceilings stay unchanged. No new recurring service cost.
