# #6490 Training Seen Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> for den anbefalede sekventielle udførelse efter ejerens planreview og build-go.
> superpowers:subagent-driven-development er kun et alternativ, hvis ejeren vælger
> det; projektets codex-wave-kontrakt gælder da. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Erstat træningshistorikkens dyre GIN-afhængige eksistensopslag med en
præcis, transaktionel projektion, og dokumentér korrekthed og kapacitet før prod-go.

**Architecture:** En tekstnøgle og rapporttæller pr. rider_id-streng afleder præcis
det gamle JSON-match. Statement-triggere vedligeholder tællerne; en markør på
kilderækken gør backfill genoptagelig under samtidige writes. Gamle læsere og
GIN består, indtil paritet og separate aktiveringsmandater er på plads.

**Tech Stack:** Repoets Node-runtime, node:test, eksisterende PGlite, PostgreSQL 17,
PowerShell 7, psql og #5904's staging-wrapper. Ingen ny runtime-afhængighed.

**Spec:** [Ejer-godkendt design](../specs/2026-10-11-6490-training-seen-design.md).
SSOT: [TRAINING_RULES](../../TRAINING_RULES.md),
[MIGRATIONS](../../MIGRATIONS.md), [DATA_API_GRANTS](../../DATA_API_GRANTS.md).
Ejer-go til design og denne planopgave er
[registreret på #6490](https://github.com/NicolaiDolmer/CyclingZone/issues/6490#issuecomment-6113868462).

## Global Constraints

- Dette er **kun planen**. Ingen implementation, stagingkørsel, prodændring eller
  indeksfjernelse er bestilt i denne tur. Alle checkbokse nedenfor er fremtidige.
- Ingen DROP INDEX, flag-flip, højere team-concurrency, ændret spillertekst,
  træningsformel, historikfjernelse eller ny jobkø i leverancerne.
- GIN-sletning kræver særskilt ejer-go; også en benchmarkvariant uden GIN må ikke
  fjerne det eksisterende indeks. Byg i stedet en ny, disponibel testdatabase uden
  indekset fra start, når testmiljø og mandat er på plads.
- SQL-udkast ligger i `database/manual/6490/`, uden for auto-migrate-globben.
  `.github/workflows/auto-migrate.yml` kører alle nye `database/2026-*.sql` på main;
  flytning dertil, merge af aktiverende kode og apply kræver et senere prodmandat.
- `rider_key text COLLATE "C" PRIMARY KEY`; `report_count bigint >= 0`;
  `report_count > 0` betyder hit. Ingen UUID-normalisering eller FK til riders.
- `training_day_runs.training_seen_indexed boolean NOT NULL DEFAULT false` er
  intern backfill-status. Rapport, markør og tæller skal committe atomisk.
- Ingen klientadgang. RLS og eksplicitte grants, også til service_role; invoker
  foretrækkes. SECURITY DEFINER kræver konkret begrundelse og bevarede sikkerhedskrav.
- Faste testure; ingen afhængighed af væguret. Historiske SQL-migrationer ændres
  ikke. Nye tests i denne plan er `.ts`; eksisterende tests bevarer filtype.
- Én implementerende lane anbefales, uafhængigt review pr. leverance. Maks to tunge
  checks via `scripts/verify-lock.ps1`; ingen parallel mutation af delt staging.
- Alle commits bag branch-guarden og push umiddelbart bagefter. Hoved-checkoutet,
  NOW, MASTERPLAN og andre sessioners claims/processer røres ikke.

## Leverancer og rækkefølge

| Leverance | Selvstændigt resultat | Afhænger af | Må aktiveres i prod? |
|---|---|---|---|
| L1: projektion | SQL-udkast + testet tekstparitet og atomiske triggere | Plan/build-go | Nej |
| L2: backfill | Genoptagelig optælling + fuld paritetskontrol | L1 | Nej |
| L3: læserskift | Kontrolleret skift + recovery-/restore-kompatibilitet | L2 | Nej |
| L4: databasebevis | Reelle concurrent-session-tests, ikke kun PGlite | L1–L3, testmiljø-go | Nej |
| L5: kapacitetsbevis | 1×/10× A/B-rapport + konkret beslutningspakke | L4, kapacitetsmiljø-go | Nej |

L1–L3 afleveres i separate draft-PR'er med `Refs #6490`, aldrig `Closes`.
Afhængige PR'er kan baseres på forrige leverances branch og reviewes som delta;
ingen af dem merges som genvej til at teste i prod. L4/L5 kan have egne test-PR'er.
Issue-opdeling sker kun ved faktisk behov og efter obligatorisk dubletsøgning.

## Review Focus

1. Råt kompensationsinput kontra UUID-cast: samme hit/ikke-hit før og efter (L1/L3).
2. Backfill overser en låst gammel rapport eller dobbeltregner en opdatering (L2/L4).
3. Sletning, rollback eller cascade fjerner den sidste reference (L1/L3/L4).
4. Replica-restore importerer true-markører med forkerte tællere (L3).
5. Grøn løbsharness uden fuld træning eller percentiler giver falsk kapacitets-go (L5).

## L2: Backfill og fuld paritetskontrol

**Filer:** Opret `database/manual/6490/training-seen-backfill.sql`,
`database/manual/6490/training-seen-parity.sql`,
`backend/lib/trainingSeenBackfill6490.integration.test.ts`,
`backend/scripts/staging/backfillTrainingSeen6490.mjs` og
`backend/scripts/staging/backfillTrainingSeen6490.test.ts`.
Opdatér samme SSOT med backfill/readiness, ikke en påstand om live-status.

**Interfaces:** SQL `public.training_seen_backfill_batch(p_limit integer)
RETURNS TABLE(processed bigint, remaining bigint)` har ingen default; `p_limit`
skal være et heltal i 1..1000. Dette er et teknisk sikkerhedsloft, ikke målt
throughput eller valgt driftsværdi. Resultatet `processed=0` er ikke færdig,
hvis en række er låst. `public.training_seen_parity()` returnerer én række:
`unindexed bigint, missing_keys bigint, extra_keys bigint, wrong_counts bigint`.
Sammenlign source-counts og projektion i samme statement/snapshot; nul-tombstones
er ikke extra_keys. `public.training_seen_assert_ready() RETURNS void` kaster,
hvis et af de fire tal er forskelligt fra nul. Alle tre service-only/invoker.
Paritetsskanningen kræver også, at de forventede triggere er aktive og definitioner
matcher den versionskontrollerede kontrakt; funktionens navn alene er intet bevis.

- [ ] Skriv tests med gamle marker=false-rapporter, blandede indlemmede rækker,
  tomme rapporter, gentaget batch, afbrudt transaktion og ændringer mellem batches.
  Test separat hver paritetsfejl, herunder korrekt boolean men forkert count.
- [ ] Kør rød. Implementér batch via row locks/SKIP LOCKED og markør-update;
  lad L1-triggerne gøre optællingen. Ingen separat count-upsert fra runneren.
  Genbesøg låste rækker; en id-cursor må ikke erklære dem færdige.
- [ ] Implementér runnerens CLI `--batch-size N --pause-ms N --max-batches N
  --out FILE`; alle er obligatoriske. Valider hele tal: batch 1..1000,
  pause 0..60000 ms, max-batches 1..10000. Ingen prod-mode. Den kræver den eksisterende loadtest-wrapper og
  isolationstest før første forbindelse. Log kun aggregeret progress og fast
  fejlkode; ingen URL, credentials, reportindhold eller persondata.
  Progress er en observation; kildemarkørerne er autoriteten ved restart.
- [ ] Test målvalidering med fake transport: prod-ref, manglende wrapper,
  redirect/ukendt target og forkert schema giver nul mutationskald. Et tomt batch
  med remaining>0 giver afventning/ikke-klar, ikke exit-success som færdig backfill.
- [ ] Kør grøn og test SQL to gange. Aflever L2 med præcis readiness-output-kontrakt;
  L4 ejer beviset for reelle samtidige sessions. Ingen backfill køres i prod.

**Kommandoer:**
`node --test backend/lib/trainingSeenBackfill6490.integration.test.ts`
og `node --test backend/scripts/staging/backfillTrainingSeen6490.test.ts`.

## L4: Rigtige PostgreSQL-transaktioner

**Filer:** Opret `backend/scripts/staging/verifyTrainingSeen6490.mjs`,
`backend/scripts/staging/verifyTrainingSeen6490.test.ts` og
`docs/snapshots/6490/README.md` med evidensformat, uden private fixturedata.

**Interfaces:** Runneren har `--mode concurrency --clock ISO --out FILE`, kræver
samme rene wrappermiljø som L2 og bruger separate psql-forbindelser med credentials
i child environment, aldrig i log eller rapport. Den rapporterer
`{status: 'PASS'|'FAIL'|'BLOCKED', cases: [...], parity, targetRef, commit}`.
Manglende native PostgreSQL/psql/miljøadgang er BLOCKED, aldrig et grønt skip.
PGlite bruges fortsat til hurtige tests, ikke som multi-session-bevis.

- [ ] Skriv runner-tests: afvis forkerte targets inden spawn, kontrollerede barriers
  skal koordinere mindst to sessioner, SQL-fejl skal propagere og cleanup må kun
  berøre runnerens egne fixture-id'er. Ingen generel process-kill eller table-truncate.
- [ ] Implementér cases: låst gammel række under SKIP LOCKED; update før/under
  backfill; delete før/efter optælling; to hold med delte tekstnøgler; modsatrettet
  batchorden; UPSERT med både insert/update; rollback efter triggerarbejde;
  læserskift samtidig med writes og assert_ready under manglende trigger.
  Brug synlige barriers/lock-observationer, ikke heldige sleeps som korrekthedsbevis.
- [ ] Kør native cases i autoriseret isoleret testmiljø med fast fixturemanifest.
  Krav: ingen deadlocks, ingen tabte updates, rollback fuldstændig og fuld paritet
  nul efter hvert case. Timeout er FAIL/BLOCKED med årsag, aldrig bestået.
- [ ] Gem aggregeret resultat i GitHub/snapshot og få uafhængigt review af SQL,
  lock-orden og recovery. Alle write- og grantcases skal være udført, ikke blot

## Fælles verifikation og commits

Hver leverance følger rød test → minimal implementation → grøn test → selvstændigt
review → rettelser → commit/push. Brug de konkrete taskkommandoer ovenfor. For SQL
desuden idempotens to gange, eksplicit grants-audit på de ændrede manual-filer og
eksisterende SQL-lints. Kør både `scripts/preflight-pr.ps1` og **TIER FULL**
`scripts/verify-local.ps1` for backend/SQL-leverancer, med verify-lock om tunge checks.
Frontend/i18n ændres ikke; hvis det bliver nødvendigt, stop for scope og tilføj
repoets krævede frontend/e2e-verifikation.

```powershell
& ./scripts/verify-lock.ps1 -Max 2 -- pwsh -NoProfile -File scripts/verify-local.ps1
& ./scripts/verify-lock.ps1 -Max 2 -- pwsh -NoProfile -File scripts/preflight-pr.ps1
```

Før commit kontrolleres staged filliste og `git --no-pager diff --cached --check`.
Kør `bash scripts/guard-commit-branch.sh <forventet-branch> <worktree>` og commit
kun ved exit 0, derefter straks push. GitHub-kommentar dokumenterer testresultat,
resterende gate og næste leverance. Ingen auto-merge; main kan udløse deployment.
Planens nye helpernavne og CLI-kontrakter er beslutninger for implementation,

## Planreview og slutpunkt

Selvreview: design §§1–3 → L1; §4 → L1/L2/L4; §5 → L2/L3 og stopgrænsen;
§6 → L1–L5; §7 → hver PR/issue-handoff. Alle fem Review Focus-punkter har egne
tests. SQL-signatures, tekstnøgle, markør og readiness-output er fælles kontrakter.

Efter L5 stopper dette forløb ved en beslutningsklar ejerpakke. Promovering til
auto-migrate, prod-backfill, prod-læserskift og GIN-drop er ikke udførelsestrin her.
De kræver senere konkrete mandater; GIN-drop får altid sit særskilte go.

Denne planleverance ændrer kun docs. Patch notes og FEATURE_REGISTRY er ikke
nødvendige. Ved senere implementation opdateres områdets SSOT i samme PR, og
eventuel spillerrettet patch note vurderes før release. Intet nyt CI-vagtsystem
indføres. Ejeren reviewer planen og vælger udførelse før build.
