# #6765 M1: local PG17 evidence

Design: [PR #6849](https://github.com/NicolaiDolmer/CyclingZone/pull/6849).
Build mandate: owner request, 19 October 2026; [issue claim](https://github.com/NicolaiDolmer/CyclingZone/issues/6765#issuecomment-6265108508).
Only additive shadow maintenance is included. Legacy matviews remain the reader
and heartbeat contract. No staging/production write or reader swap was performed.

## Reproduction

Native PostgreSQL 17.11 on Windows, disposable cluster bound to 127.0.0.1.
The runner asserts major version 17, uses synthetic IDs and stops its own cluster.
PG_BIN can select a different PG17 bin directory; PG_PORT selects a free port.
Run behind the shared verify semaphore:

    pwsh -File scripts/verify-lock.ps1 -Max 2 -- node backend/scripts/verifyRankingDeltas6765.mjs --baseline
    pwsh -File scripts/verify-lock.ps1 -Max 2 -- node backend/scripts/verifyRankingDeltas6765.mjs --benchmark-only
    pwsh -File scripts/verify-lock.ps1 -Max 2 -- node backend/scripts/verifyRankingDeltas6765.mjs --quick --concurrency
    pwsh -File scripts/verify-lock.ps1 -Max 2 -- node --test backend/lib/testdb/rankingDeltas6765.integration.test.ts

Without switches the native runner also checks all mutation scenarios at volume.
The four reference SELECTs are extracted directly from the existing #5535 and
#4620 migration files, independently of the new processor. Every comparison
uses EXCEPT ALL in both directions, on all columns and the same source data.

## Before and after

Deterministic fixture: 2,304,000 results, 1,200 races, 1,920 results per race,
four seasons, three squads, stage races and single races, nullable rider/team,
points and prizes. This is local synthetic volume, not a staging performance SLA.
Read-only production catalog verification on 19 October confirmed
race_results.points_earned=int4 and prize_money=int8, matching the fixture and
the contribution SUM types. No production data or schema was changed.

The pre-implementation baseline was 7,147.68 / 9,775.20 / 11,654.04 ms.
The final paired run rebuilt that fixture from scratch:

| Operation | Three request times, ms | Median, ms |
|---|---|---:|
| Four legacy concurrent refreshes | 7,628.92 / 4,732.89 / 4,258.68 | 4,732.89 |
| Apply after changing one race | 795.49 / 1,992.23 / 1,380.48 | 1,380.48 |

Median improvement: approximately 3.4x (71% less time). Measurements include
psql startup/transport and were taken under the shared two-slot verification
limit; cache and concurrent work explain the range. Three samples are not p95.
Each changed-race run had zero differences against fresh full SELECTs.

Backfill requests: 484.74 / 5,263.79 / 9,684.54 / 12,583.81 / 9,493.61 /
6,729.13 / 6,456.00 ms. The first request expands repair work into race IDs;
later requests process at most 200 queued items. No backfill runs inside the
DDL transaction. Maximum observed request was 12.58 s, below the 60 s transport
budget. Transfer fanout also becomes race items, retaining bounded source scans.

## Correctness and operations

The SQL suite covers all four outputs and aggregate columns, NULL sums and
nullable seasons, senior/U23/junior, duplicate events, migration replay,
transaction rollback/retry, race replay, metadata moves, historical transfers,
multiple transfers, deletion after transfer across batches, rider deletion,
TRUNCATE/rebuild, service-only grants and stale-token rejection.
Parity RPC tests prove equal/different/pending generation handling.

Coordinator tests cover additive migration absence, daily parity scheduling with
explicit time, Sentry reporting and lease renewal before/between/after shadow
RPCs. The existing 34 coordinator tests remain covered alongside five helper
tests. Legacy completion is independent of shadow correctness/failure.

The independent reviewer reproduced and then verified fixes for old-team
invalidation after deleting the last contribution, TRUNCATE riders, and lease
expiry during slow successful shadow work. No remaining actionable findings.

Native concurrency: the processor transaction was held open for three seconds;
a stage insert succeeded with lock_timeout=100ms. The server had log_lock_waits
enabled with deadlock_timeout=100ms; zero waits over 100ms were logged in that
scenario. In the final native run the stage request took 120.34 ms including
client startup; this is not a 120ms lock wait. A conflicting writer caused the
migration to fail after 5,174.08 ms with lock_timeout; retry after releasing
the writer succeeded and parity remained zero.

Final focused gates: 18/18 SQL integration tests, 39/39 coordinator/helper tests,
strict helper typecheck, migration idempotency/lock/SECURITY DEFINER/grant audits
and full preflight passed. Frontend unit tests: 4,819/4,819 passed; build passed.
The FULL script's initial existing wave-policy timing failure passed on rerun;
that rerun then hit Windows ENAMETOOLONG passing 970 backend test paths.
The same remaining files are verified in bounded argument batches, preserving
per-file process isolation and the separate economyEngine pass. Final batch
results are recorded in the PR. The 967 remaining backend files were all run:
the only failure was missing carry-over classification for the five new derived
tables. They are now explicitly NOT_MANAGER_SETUP (historical output, never
copied); the six carry-over registry checks pass after that correction.

The GitHub review also found that a completed mismatch skipped the daily
timestamp, causing repeated expensive checks/alerts. A failing explicit-clock
regression proved this; both equal and different completed checks now record
their time, while pending work retries and staging's every-pass override remain.

## Release boundary

M1 alone adds work beside the legacy refreshes; the production refresh-time
saving begins at M2. Claude must apply/measure on staging before production,
verify grants/schema and queue progress after apply, and enable per-pass staging
parity through RANKING_SHADOW_PARITY_EVERY_PASS=true. This setting is not changed
by this PR. Production checks run daily per client and after process restart.

M2 remains separate: design gates T1-T7, staging p95-race target, three days
without parity findings on staging and two days in production, plus owner-go.
Those gates are not claimed satisfied by these local results.

Rollback M1: remove the twelve ranking_delta_* triggers, then its two RPCs,
enqueue_ranking_delta and the six ranking_* shadow tables/queue. Legacy objects
need no recreation. Execute rollback only through the normal owner/SQL process.
Patch notes exempt: M1 changes no player-visible output, text, flag or API.
